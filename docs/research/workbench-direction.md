# 工作台方向（2026-09-20 定案，2026-09-27 改为两期）

定位：方向定案与路线记录，具体任务与实现状态只看 [`任务看板`](../tasks/README.md)。第 7 节是唯一的顺序与触发来源。2026-09-20 定案合并 gsc 做内部数据工作台；2026-09-27 按产品讨论改为「给 topuplist 运营用的 AI 工作台、分两期、上云，gsc 延后」。产品层的做什么、为什么、不做什么在 Claude Docs《Agent 产品方案》（链接见 [`协作流程`](../workflow.md)），本文只记路线、边界与否决项。讨论方向或立项时按问题读本文：产品边界看第 1 节，顺序与触发看第 7 节，路线变化看第 8 节；状态查 [`任务看板`](../tasks/README.md)，历史阶段才查 [`roadmap`](../roadmap.md)，其他任务不例行加载。

## 1. 结论

给 topuplist 运营做一个 AI 工作台：**一个对话入口，agent 自己判断是回答还是做页面**，部署在香港云服务器。首批用户是 1～3 个运营，目标 5～30 人。分两期：第一期把运营的日常对话搬进来（登录、联网、部署），第二期让运营用对话做出、保存并反复修改自己的数据页面（「我的页面」）。gsc 网站当作不存在、以后下架，它的页面迁移与完整数据层延后。本 runtime 以此为唯一真实负载，路线 R2～R5 的触发全部来自它。

## 2. 为什么

- 运营想看的数据视图，每次都要用户写代码、部署；之后加筛选、改样式也全压在用户身上，改的次数比新做的多。
- 运营大多用免费 GPT 写英文文章、问知识、查资料，有次数限制、对话分散；公司中转站已接好，对话先到这里，以后的记忆与团队共享才有基础。
- 运营说得清业务指标，但不知道 GSC / GA4 能做到什么；用户现在靠 Claude Code + Google Developer Knowledge MCP 当这个翻译，产品要让 agent 接手。
- runtime 没有真实使用，路线 R2～R5 的进入条件全是「真实使用」，没有负载永远走不到。

## 3. 产品形态

| 应用 | 定位 | 用户 | 内容 |
| --- | --- | --- | --- |
| `apps/web` | 工作台 | 运营、用户 | 登录；对话（联网搜索）；第二期加「我的页面」与页面旁对话 |
| `apps/admin` | 管理台 | 用户 | 账号、模型与中转站、Google 接入（第二期）、Runtime 可观测（现有） |

判断一个功能放哪：运营天天用的放工作台，偶尔配一次的放管理台。不分 chat / work 模式（对照 Claude 2026-09-16 合并 Chat 与 Cowork：用户烦的是判断任务该放哪）。

## 4. agent 对话做什么

- **日常对话**：写文章、问知识、翻译靠模型本身；看新闻、查网站靠联网搜索与读网页，回答附来源链接。
- **先判断能不能做**：数据有没有、API 支不支持、口径对不对。能做先用业务语言复述、运营确认再做；不能做说明原因并给最接近的替代方案（例：小时数据只有最近 10 天 → 整月按天 + 最近 10 天按小时）。
- **做页面**（第二期）：agent 在沙箱容器里写页面并试跑；页面记住取数方式，每次打开重新取数、不经模型，标注「数据截至何时」；页面旁的对话随时改。
- **底座**（第二期）：两个通用查询工具（GSC Search Analytics：维度 × 过滤 × 时间窗；GA4 Data API：维度 × 指标 × 时间窗）；能力边界来自工具清单与 GA4 `getMetadata`，不靠开发用的知识库 MCP。
- **聊天还是构建**：模型看到工具清单自行决定，不另做分类。

## 5. 边界

- 部署在香港云服务器（腾讯云轻量），域名 `askkuro.com`（产品名 Kuro，2026-09-27 注册）：连 Google 不用代理，Let's Encrypt 证书由 Caddy 自动续期；管理台在 `/admin/`。鉴权在后端，未登录请求 API 一律拒绝，不是前端拦截。上线前提：公司同意数据与 Google 凭据放在公司之外的服务器。
- 凭据只在后端；沙箱容器不出网、不碰凭据，数据由工具取好放进工作区。
- 不让模型自由写 SQL；工具目录外的分析第一版直接说做不了。
- 查询工具自带缓存与配额控制（GSC 每分钟限流、URL Inspection 每日 2,000、GA4 按 token 计日配额），不裸打 Google。
- 通用对话功能只在「运营因为缺它回去用 GPT」时才补，不照 GPT 的功能清单抄。
- 仍不引入 Multi-agent、LangGraph / workflow engine、微调。

## 6. gsc 延后

gsc 网站继续跑到被替代为止，产品上当作不存在。第二期只做需要的查询工具，可以复用 `dashboard/src/lib/` 里的 OAuth、查询与口径代码，不整体迁移。延后到「后」行的：完整数据层（SQLite 换 Postgres、同步调度）、收录任务与观察清单、官方页面迁移（运营不能改的固定页面，体量大、形式未定）、Python CLI 退役。

gsc 现状备查：Python CLI 1,900 行；看板数据层 `dashboard/src/lib/` 8,000 行 TS（OAuth、GSC / GA4 查询、缓存、配额、口径、SQLite、同步、收录）；看板页面 `dashboard/src/app/` 13,000 行 React。

上下文管理（E1 / E3，2026-09-28 起）：runtime 给模型的历史只有之前的「问题 + 最终回答」（#119 / #152 的设计，当时只有站内文章工具），用户实测同一对话连续问同一问题，每次都重新搜索，像「没有记忆」。对照 opencode、Claude、Codex、Pi 等主流做法（[context-management.md](./context-management.md)），核心机制照抄成熟方案。E1（#218）原样带回之前问答的工具记录，同时删掉「单次最多调用模型 / 工具」「历史最多读取条数」三项配置，一次问答不限步数（照抄 Pi / Codex），只留「单次最长时间」兜底。2026-09-29 定：前台不显示用量、不做手动压缩（原 E2 取消），理由是我们给运营做云端持续对话，不是给开发者的工具，Claude、ChatGPT 网页端同样不显示；E3 照抄 Pi 做后台静默压缩（问答之间与问答进行中都能压缩，超限先压缩再重试一次），兼容以后的沙箱写代码。原「后」行的 compaction 提前到 E3。都属于技术延伸、不是产品需求，立项前单独讨论细节。排在 D 之后、第 0.5 档之前（影响模型行为，0.5 测的正是模型行为）。2026-09-30 E3 立为 #220：计数改为「同一问答内上次 usage + 新增部分按字节数 ÷ 4 粗估，每次问答第 1 次调用全量粗估」，删本地分词器与「删最旧问答 + 截短工具结果」兜底；两层压缩（历史压缩只覆盖已结束的问答，本轮压缩撑住沙箱写页面的长工具循环、结束后按压缩后形态还原）；回答结束后超过 0.8 × 触发线在后台提前压缩。Pi 的自动压缩其实是同步的，后台提前压缩是我们加的。E3 完成后与 #212、#214、#216、#218 一起上线。

生成中新建会话与跨会话并发（2026-09-28 确认，2026-10-01 立为 #222）：生成中可立即新建或切换会话并发送，旧回答继续，各会话输出与停止独立；后端每条请求独立运行。用户决定暂缓额外一轮第 0.5 档验证，先完成此任务；范围只在工作区存续期间，同会话仍只允许一个活动请求，刷新/关页续跑不在本次。实现状态见[任务看板](../tasks/README.md)。

单文件 HTML 直接预览（2026-10-01 用户确认，#224）：先补浏览器内的展示能力，完整 HTML 从代码卡片打开独立右侧面板，聊天/预览可调宽、关闭与重开，原文可下载；普通代码与 HTML 片段不提供预览入口。本轮先支持静态 HTML/CSS/SVG 与原生动画，不执行 JavaScript，复制/下载保留完整原文；JS 交互另讨论网络边界。此步不创建服务端沙箱，不增加执行/文件工具或独立产物持久化；后续能力另行讨论，第二期与 M1 的触发关系不因此自动改变。当前状态见[任务看板](../tasks/README.md)。

鉴权：2026-09-23 曾决定暂缓到「开放同事」；2026-09-27 起随第一期上线进入第 1 档，因为服务器在公网、多个运营共用。

长会话首轮分词（2026-09-23）：首轮同步分词会阻塞事件循环，实测 1000 条 × 约 2.4k 字符的历史要 4.6s；当前 dev 库最长的会话只有 18 条，暂不处理。2026-09-30 #218 实测（隔离测试库造数据，每次问答 1 次搜索 + 2 次读网页，observation 取工具上限 8,000 / 20,000 字）：历史带回工具记录后，5 次问答首轮 plan 约 95ms；20 次问答（超预算，裁到 32 / 40 条、约 25 万 token）首轮约 1.7s、之后每轮约 0.3s，越过了 500ms 这条线；读历史 Step 7～10ms（1.35MB，开调试抓取也一样）。这是造的数据，真实会话还没到（dev 库最长的带工具会话 3 次问答）；#220 删掉分词器、改为粗估后解决：同样的 20 次问答（工具结果取上限长度、估算约 74.6 万 token）首轮 plan 0.5～0.6ms，读历史 12～28ms。

### 团队协作清单（2026-09-21 补，2026-09-27 移到「后」行）

用户提出多人协作：每人有自己的对话，团队有项目，讨论产物存成团队知识库。判断：这些是 ChatGPT Team / Claude Projects 的标配，值得做但不是亮点；亮点仍是 agent 拿公司数据出页面，团队功能围着它转。个人对话隔离已随第一期登录做掉，其余等运营真的要分享时再做，单用户时期不为想象中的用户建表。只写做什么和为什么，表与接口到 Issue 定。

| 项 | 做什么 | 为什么 |
| --- | --- | --- |
| 分享 | 本人可把对话或页面生成系统内链接，需登录打开 | 第一版不做，等真实需求 |
| 团队项目 | 团队项目下的对话成员互相可见，可以从同事的对话接着问 | 只读分享价值低，「以这个分析为起点」才省重复提问 |
| 团队口径 | 每个团队一段固定说明（站点范围、指标定义、时区、常用维度），该团队所有对话都带上 | 两个人问同一问题得同一口径；成本一个文本框。对照 Claude Projects 的 project instructions |
| 共享知识库 | 对话产物一键存为知识库文档，agent 检索按当前用户可见范围过滤；检索方案立 Issue 时重新选型（原文章检索管线已于 2026-09-26 删除） | 用户说的「共享记忆」就是这一条，不做独立 Memory 子系统 |
| 产物带出处 | 存进知识库的分析必带数据时间窗与来源对话；分析产物只作参考、数字重新算 | AI 产物进知识库最常见的坑：旧数字被当事实引用 |

## 9. 否决的选项

| 选项 | 否决理由 |
| --- | --- |
| gsc 安装我们的包 | 栈不通（Python + Next）；循环要 Postgres 与流端点，不是库；`packages/agent` 不存在 |
| 按我们规范重写 gsc 整体 | 页面重写纯成本；数据层按第二期需要取用 |
| 只做规格驱动图表、不要容器 | 用户要 agent 自己试错的能力；容器进第 2 档 |
| 懒路径：gsc 做 MCP server，同事用 Claude.ai | 数据经第三方、按席位付费；作为基线记录 |
| 提前分包 | 一个消费者；接口取决于 operation 模型；搬完是半空的包 |
| 对话放管理台或 gsc 看板 | 管理台是运维面；gsc 看板要下架 |
| 分 chat / work 两个模式 | 非技术用户不该先判断任务放哪；Claude 2026-09-16 已因此合并 |
| 多租户 | 一家公司，多用户够用；租户隔离每张表带 tenantId、要单独验证，是想象中的需求 |
| 独立 Memory 子系统做「共享记忆」 | 团队知识库已覆盖；长期 Memory 仍按能力缺口规则等真实卡住 |
