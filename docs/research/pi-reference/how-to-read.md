# 给实现智能体的使用说明

## 这个目录为什么存在

用户不读 Pi 代码，也不需要 AI 把 Pi 讲给他听。用户完成自己项目的源码学习后，会让 AI 按 [roadmap](./roadmap.md) 的顺序替他实现云端 Agent；本目录是 AI 动手前查证据的素材库，避免每个新会话重复调研、套用旧版 Pi 印象或直接照搬 CLI。

研究准备完成不代表重构已获批准。正式任务状态看 `docs/tasks/README.md`，已建的 #115 → #116 → #117 不由这里改动。

## 新会话读取顺序

1. 读本目录 `README.md` 的主题路由，按这次要实现的问题选模块；遇到不熟的词先查 `glossary.md`，不要凭名字猜（`deferred`、`attachment`、`checkpoint` 在不同层含义不同）。
2. 读 `source-snapshot.md`，核实两个 checkout 的 HEAD。
3. 只读对应模块说明及其中的一条真实源码链；需要总体定位再开图。
4. 对照 `current-agent-mapping.md` 找到我们当前实现的位置，再看 `roadmap.md` 里这一步的进入条件与证明完成。

不要把全目录一次塞进模型上下文。模块说明是导航和事实索引，原始代码是最终证据。`modules/*-coverage.md` 用来核实研究边界。

## 动手前的对照

每次只针对一个场景：直接回答；一次工具调用；同轮多个工具；断流；用户 Abort；观察者断开；进程重启；工具结果未记录；压缩；切换分支；重新附着；插件换代。

对照按下面顺序写在方案里，给用户看的只有最后两行：

```text
本段问题 → Pi 文件/符号 → 输入/输出/控制权 → 成功与失败分支 → 谁拥有状态
→ 我们当前代码的位置与差异 → 保留的不变量与最小改动
```

- 区分模型请求、Provider 流事件、内存 reducer、durable entry、UI projection、transport frame。
- 对 `stream()`、async generator、事件订阅，查清实际何时发请求；不要套用"首次 next 才启动"的通则。
- `replay` 要说明重放什么：还原视图、还原模型上下文、继续 operation、重新执行外部副作用是不同能力。
- 取消要说明取消谁：HTTP/RPC 等待者、订阅、lane operation、模型请求、工具进程。
- 图只用于定位，节点不能替代函数证据。图中标为"候选"的内容不能说成当前实现。
- 纯观测字段才可说"不影响模型输入或控制流"；先查其消费者，不能仅凭 `event` / `trace` 命名判断。

## 提出改动前

给出当前具体问题、Pi 的实际做法、我们保留的不变量、最小改动范围和可验证失败场景。目录更整齐不是单独的重构理由；NestJS DI 已解决的组合问题不另写一套 Chord；现有 NDJSON 能满足的场景不自动换成 CBOR。

用户决定实现范围后才进入仓库正式流程。不自动 commit、push 或建 Issue。向用户汇报只说结论、影响与需要他做的选择，一次不超过两条，不讲 Pi 机制细节。
