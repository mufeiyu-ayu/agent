# 协作工作流

正式交付、建 Issue、处理 PR 或状态收口时读取。基线见根 `AGENTS.md`；工具差异见 `CLAUDE.md`、`.pi/APPEND_SYSTEM.md` 或 `.codex/INSTRUCTIONS.md`。流程由同一角色实现、Review 与验收，不依赖另一个模型或远程自动 Review。

## 1. 默认范围与授权

| 用户请求 | 范围与停止点 |
| --- | --- |
| 源码阅读、讨论、方案草稿、本地实验、小改动 | 按当前请求处理；不自动切分支、commit、push、建 PR 或改任务状态 |
| 「聊产品」「这个功能怎么设计」 | 用 `product-brainstorming` 讨论；拍板的产品结论按 `write-spec` 更新唯一产品方案，不自动建 Issue |
| 「下一步做什么」「下一阶段做什么」 | 读当前看板、最新代码与方向第 7 节，提议一个任务；该步参照与证明完成查 Pi roadmap；不建 Issue |
| 「建 Issue」「把刚才聊的立项」 | 以本会话已确认的目标、范围与验收建 Issue，最新正文保存完整规格 |
| 「完成 Issue #N」「读取 Issue #N 并实现」 | 独立任务分支，实现、验证、commit 前 Review、push、PR、验收；全部 PASS 后合并、清理任务分支、收口 docs |
| 「处理 PR #N 的 Review」 | `github-pr-review-fix`：核对外部评论、修复真问题、验证、commit、push 原 PR；不含合并 |
| docs 更新 / 收口 / 写入 master | 本地更新只编辑；明确授权提交时，docs-only 可直写 master；push、状态收口取本次授权，不包含代码或运行策略变更 |

用户可缩小为只读、只到本地验证、不 commit、停在 PR、Draft 或人工验收。已给授权在范围未变时继续有效；「继续」从已授权的停止点推进，不撤销先前的范围限制。讨论到立项通常在一个会话，实现到收口通常另开会话；这是协作节奏，不是强制门槛。

小改动的本地编辑不要求 Issue 或分支；用户要求提交交付时，非高风险、单一关注点的小改动可不建 Issue，但交付走独立分支、Review 和授权的合并。正式代码任务走 Issue / PR，实施前切独立任务分支，不直接在 master 实现或交付。docs-only 的例外见第 3 节。

## 2. 正式交付与硬约束

1. **规格与路线**：Issue 最新正文是唯一实现规格，开工前及实现中规格变化时，将用户已确认的补充决定并入正文后继续，不以评论或链接代替，也不对已明确的决定重复确认。看板是状态来源，方向第 7 节是顺序来源；偏离路线先说明位置与代价，再由用户决定。只完成一个任务单元。产品方案只有 [Claude Docs《Agent 产品方案》](https://claude.ai/code/artifact/7661407e-99ef-4336-be08-3d89e2d9331d)，写做什么、为什么、给谁用、不做什么与怎样算完成，只标 P0 / P1 / P2，不排任务顺序；仓库不放 PRD。
2. **范围与实现**：保留他人工作区、staged 内容和其他任务；不能安全隔离时暂停。更新主分支只接受 fast-forward，正式任务分支为 `<分支前缀>/issue-N-<slug>`。不为未来用例加抽象，一个实现的接口不抽、一个消费者的模块不拆；Issue 明确不过度设计边界，Review 处理超出范围的抽象。
3. **验证**：按 Issue AC、根基线和 `docs/testing.md` 选最小必要检查，修复本次引入的失败并复查。高风险指持久化、恢复、owner fencing、审批、鉴权或 migration；Review 档位按工具适配，AC 必含路线该步「证明完成」的故障注入场景，无对应步骤则自拟相关故障 AC。
4. **本地 Review**：验证后、commit 前审本任务已暂存 diff，并给出需求背景。工具实际覆盖更广时，按任务范围和真实代码分拣，不能声称工具只审暂存区。真问题在授权范围内自行修复、定向验证、重新暂存；已确认规格不为 Review 反向改动。无证据、存量、范围外、误报或过度设计建议不修，一句话说明。复审最多两轮，未解决的阻断问题不能当通过或继续合并；docs-only 跳过独立代码 Review。
5. **GitHub 交付**：实际交付前用 `gh auth status --hostname github.com` 与 `git push --dry-run origin HEAD` 预检凭据，不输出 token。认证或权限失败保留本地成果并报告，不改用 API、Connector 或手工上传绕过。commit 只含本任务文件，push 任务分支，PR 默认 Ready；未完成、验证失败、受阻或用户要求才 Draft。PR 描述包含 `Closes #N`、行为变化、验证、Review 结论与实际风险，复杂任务补阅读顺序。
6. **验收**：本会话基于 PR 最新代码 head，对最新 Issue 每条 AC 给 PASS / FAIL / 未验证及证据；测试成功或代码合理不单独构成 PASS。任一 FAIL / 未验证停在 PR，不合并。云端 bot、GitHub Actions 和额外远程 Review 不作必需门槛；新证据仍应核实。
7. **验收后的记录**：实现且必要验证通过可记「已实现 / 待验收」；全部 AC PASS 且包含状态更新授权时可记「已实现 / 已通过」，PR 未合并时看板仍不标 Completed。需要在原 PR 追加状态记录时，只允许 `docs/tasks/**` 的事实更新，核对新增 diff 并记录最终远程 head；再有代码或其他行为改动必须重新验收。work-log 不记录验收过程或尚未发生的合并。
8. **合并**：确认远程 head 等于验收 head，或仅多出第 7 条已核对的状态提交，再执行已授权的合并；fast-forward 同步本地主分支并确认合并结果确实在主分支。合并失败、结果不确定或远程代码变化时不得标 Completed。
9. **收口与清理**：已实现、全部 AC PASS、合并事实已核实且包含收口授权时，才将看板改为 Completed，说明一句话加 PR 号。按 docs-only 例外在已同步的 master 提交相关任务状态与真实 work-log；路线或触发变化才改方向，阶段满足自己的条件才归档并更新 roadmap。默认「完成 Issue」包含这些必要的 docs 提交与推送，缩小范围时遵从本次指令。只纳入本任务收口文件，保留并行改动；同步并核对远程 docs 后安全删除本任务远程 / 本地分支，不强删未合并分支。合并已成功但收口失败时报告准确停止点，不写成全部完成。

验收、状态收口、合并、分支清理是不同动作；授权范围取第 1 节与本次指令，不由测试或 Review 自动推导。用户已一并授权时不逐项重复询问。仅在规格冲突会改变方向、归属无法隔离、缺少权限 / 登录 / 环境前提或需要未授权操作时暂停；任务内技术取舍自行处理。只读 Review 不转实现。

外部 Review 评论只在用户请求时走对应 Skill；合并后到达的评论在同模块下一次立项时按证据分拣，结论写 Issue 决策记录。使用 `<review 命令>` 时不得把外部评论修复替代 commit 前检查。

## 3. 共用定义

### Issue 模板

```md
## 目标
## 当前代码事实
## 对照            # 可选：Pi / opencode / Codex 等真实实现
## 范围            # 本次要改变的行为
## 不做            # 必含不过度设计：本次不加的抽象、接口、配置项或分层
## 验收标准        # AC-01…，逐条可核对；高风险包含故障注入
## 决策记录
## 依赖与顺序
```

### 状态

实施：未开始 / 进行中 / 已实现；验收：未验收 / 待验收 / 需要修改 / 已通过。正式 Issue 的 Completed 表示已实现、已通过且 PR 已合并；看板 Completed 行只留一句话加 PR 号，验收证据在 PR。本次不含状态收口授权时只汇报验收结果。

### docs-only 直写 master

明确授权时允许：README 与文档入口、研究材料、任务状态与归档、roadmap、真实 work-log、协作规范、typo 和纯 Markdown。授权本地编辑不等于授权提交或推送。

不允许：业务行为、API / contracts、数据库 / migration / seed、Runtime / Streaming / Tool Calling、依赖 / 环境变量 / 权限、业务代码与测试、影响运行时行为的生成规格或策略。这些按代码交付流程执行。
