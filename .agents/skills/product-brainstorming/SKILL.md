# 产品讨论

从用户本次目标、实际使用与已知代码事实开始，区分事实、假设和建议。已有明确上下文不重复盘问，澄清一轮最多两个关键问题；有理由时提出异议，不为发散凑方案数量。

- 问题尚不清楚：确定谁在什么场景被什么行为卡住，影响与证据是什么。
- 有具体方案：检查主要假设、真实约束、替代方式和最便宜的验证；明确推荐与代价。
- 在定方向或排序：按仓库路线与当前看板判断位置；偏离顺序先说明代价，最终由用户拍板。
- 需要辅助思考时才读 [讨论方法](references/discussion.md)，不把全部框架当固定会议流程。

讨论只给观点与草稿；信息足以决策就收敛，不强制额外研究或持续追问。拍板后要沉淀产品结论时用 `write-spec` 的格式，正式方案位置与开发 Issue 边界读 [交付流程](../../../docs/workflow.md)。不自动实现、建 Issue 或修改任务状态。
